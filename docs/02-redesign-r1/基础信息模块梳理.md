## 一、整体架构总览

基础信息模块是生鲜配送 ERP 的"地基"，位于 `lin-distribution` 业务模块下，为报价、订单、送货等业务模块提供主数据支撑。

```
基础信息模块
├── 商品体系
│   ├── 商品分类 (t_product_category)        ← 多级树形
│   ├── 商品库 SPU (t_product_spu)           ← 标准商品定义
│   ├── 商品信息 SKU (t_product_sku)         ← 客户绑定商品实例
│   ├── 商品别名 (product_alias)             ← 全局别名，增强检索
│   └── 客户SKU映射 (customer_sku_mapping)   ← 客户叫法映射
│
├── 客户体系
│   ├── 客户 (t_customer)                    ← 客户主数据
│   └── 客户配送点 (t_customer_dept)         ← 客户下的配送部门/地址
│
├── 报价体系
│   ├── 客户报价 (t_product_sku_quote + detail)  ← 按客户的报价单
│   ├── 配送点报价 (delivery_point_price)          ← 按配送点的单价
│   └── 报价模板 (price_template + 关联表)        ← 可复用的价格模板
│
├── 取价引擎 (PriceQueryService)
│   └── 优先级: 配送点报价 > 客户报价 > 报价模板
│
└── 支撑服务
    ├── 临时商品 (temp_product)           ← 即录即用，后续转正
    └── 通用编号序列 (biz_code_seq)        ← 原子自增序列生成器
```

## 三、商品分类管理

### 3.1 表结构

**表名**: `t_product_category`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键 |
| name | VARCHAR(200) | 分类名称，唯一索引 |
| parent_id | BIGINT | 上级分类ID（0=顶级） |
| code | CHAR(10) | 分类编码，编码即层级 |
| level | TINYINT | 分类级别（1=一级，数字越大层级越深） |
| sort | INT | 排序 |
| is_deleted | TINYINT | 逻辑删除 |
| create_by / create_time | — | 审计字段 |
| update_by / update_time | — | 审计字段 |

| 方法 | 路径 | 说明 |

### 3.3 前端

**页面**: `views/product/category/index.vue`

- 树形表格展示（`el-table` + `tree-props`），支持展开/折叠
- 上级分类选择使用 `vue-treeselect` 树形下拉
- 新增子类时自动获取同级排序值 + 编码

### 3.4 核心业务逻辑

**编码生成规则** (`generateCode`):

| 层级 | 规则 | 示例 |
|------|------|------|
| 一级 | `(count + 11) × 10000` | 110000, 120000, 130000 |
| 二级 | `parentCode + (count + 1)` | 110001, 110002 |
| 三级 | `parentCode + (count + 1)` | 1100011, 1100012 |

> 编码结构体现层级：前4位是大类，后4位是子类序号。

**排序生成** (`getNextProductCategorySort`):

- 一级分类：当前一级分类数量 + 1
- 子分类：当前父级下子类数量 + 1

**删除逻辑**: 递归删除自身及所有子分类（级联逻辑删除）。

**唯一性校验**: 分类名称全局唯一（不区分层级）。

### 5.3 前端

- **助记码**：随输入自动生成拼音首字母

### 5.4 核心业务逻辑

#### 5.4.1 新增 SKU 的四种路径

```
insertProductSku(productSku):
  │
  ├─ customerId=0 & spuId=null  →  走 SPU 创建流程（间接创建 SPU + 默认 SKU）
  ├─ customerId=0 & spuId≠null  →  ❌ 非法请求，抛异常
  ├─ customerId≠0 & spuId=null  →  直接创建客户 SKU（未关联 SPU）
  └─ customerId≠0 & spuId≠null  →  创建客户 SKU 并关联 SPU
```

#### 5.4.2 SKU 编码规则

```
编码 = 客户助记码前4位 + customerId + 5位自增序号
示例: "ABC01234500001"
      ↑    ↑        ↑
    助记码  客户ID    序号(00001~99999)
```

- 客户 ID = 0 时：`"#0000000001"`
- 序号通过 `BizCodeService` 原子自增

#### 5.4.3 搜索增强

SKU 列表搜索时，`name` 参数会同时匹配：

1. `sku.name` LIKE '%keyword%'
2. `sku.mnemonic_code` LIKE '%keyword%'
3. `product_alias.alias` LIKE '%keyword%'（全局别名）
4. `customer_sku_mapping.customer_alias` LIKE '%keyword%'（客户叫法）

**排序**：有客户叫法匹配的优先展示，其次别名匹配，最后按创建时间倒序。

#### 5.4.4 唯一性

同一客户 + 同一分类下，商品名称唯一（`customer_id` + `category_id` + `name`）。

#### 核心业务逻辑

**报价单号生成**:

```
格式: BJ + yyyyMMdd + 5位序号
示例: BJ2025061300001
```

通过 `BizCodeService` 按日重置序号。前端先 `peek`（预览），提交时 `next`（消费）。

**状态流转**:

```
新增(0) ──发布──→ 发布(1) ──失效──→ 失效(2)
```

**发布时的有效期校验**:

- 如果发布时当前日期在报价有效期区间内 → `valid=1`（生效）
- 如果不在区间内 → `valid=0`（不生效，需定时任务后续激活）

**同客户唯一生效报价**:

发布新报价时，查询该客户是否有其他生效报价，如有则将其 `valid` 置为 0（失效）。

**每日定时任务** (`syncUpdateQuoteStatus`):

遍历所有有效客户，若某客户没有生效报价，则找最新报价将其发布并激活。

**创建/更新校验**:

1. 生效日期不能早于失效日期
2. 生效日期不能早于已有生效报价的失效日期（报价区间不重叠）
3. 新增时报价单号必须唯一
4. 修改时报价状态必须为"新增"，且未生效
5. 报价明细必须全部为正价

**多客户导入**:

Excel 按客户 ID 分组，每组生成一张报价单。日期区间取该客户所有行的 min(生效) ~ max(失效)。

## 九、取价引擎

### 9.1 API

```
GET /price/query?customerId=1&deliveryPointId=2&skuId=3&deliveryDate=2025-06-13
```

权限要求：`order:sale:add`（仅录单时使用）。

### 9.2 取价优先级

```
第1层 ── 配送点报价 (delivery_point_price)
          WHERE delivery_point_id=? AND sku_id=? AND 日期在区间内
          ORDER BY effective_date DESC, id DESC LIMIT 1

第2层 ── 客户报价 (t_product_sku_quote_detail)
          WHERE 报价已发布(status=1) AND 客户ID=? AND sku_id=?
            AND 日期在有效期区间内
          ORDER BY effective_start_date DESC, id DESC LIMIT 1

第3层 ── 报价模板 (price_template_sku)
          查找客户绑定的模板 → 查模板SKU价格
          WHERE template_id=? AND sku_id=? AND 日期在区间内

均未命中 ── 返回空价（PriceQueryResult.empty），不自动回退为零价
```

### 9.3 取价结果

```json
{
  "skuId": 123,
  "price": 15.50,
  "source": 1,        // 1=配送点, 2=客户报价, 3=模板
  "sourceId": 456     // 对应的价格记录ID
}
```

## 十二、设计要点与痛点分析

### 12.1 设计要点

| 要点 | 说明 |
|------|------|
| **SPU/SKU 分离** | SPU 定义标准商品，SKU 按客户维度实例化，支持不同客户不同名称/规格/价格 |
| **客户自动建配送点** | 创建客户时自动创建默认配送点（parentId=0），保证客户始终有初始配送点 |
| **SPU 自动建默认 SKU** | 创建 SPU 时自动创建 customerId=0 的默认 SKU，保证 SPU 有基础记录 |
| **助记码体系** | 客户/配送点/商品均支持拼音首字母助记码，提升线下生鲜录单效率 |
| **检索增强** | 通过 product_alias + customer_sku_mapping 两张辅助表，SKU 搜索时模糊匹配多种叫法并排序 |
| **三层价格体系** | 配送点报价 > 客户报价 > 报价模板，粒度逐级递减，灵活性递增 |
| **报价生命周期** | 报价单有状态（新增→发布→失效）、有效期、定时任务兜底激活 |
| **并发安全编号** | BizCodeService 用原子 UPDATE + LAST_INSERT_ID 解决高并发编号冲突 |
| **SKU 编码含客户信息** | 编码结构体现客户归属，便于人工识别 |

### 12.2 当前痛点

| # | 痛点 | 说明 | 影响 |
|---|------|------|------|
| 1 | **SKU 与 SPU 强耦合** | 新增 SPU 自动建默认 SKU(customerId=0)，导致 SPU 操作必须经过 SKU 服务 | 代码耦合，职责不清 |
| 2 | **SKU 搜索 SQL 复杂** | 一条查询 join 三张辅助表，且包含子查询排序 | 大数据量时性能堪忧 |
| 3 | **SKU 删除无约束** | 未检查是否有关联订单/报价/配送点报价 | 数据一致性风险 |
| 4 | **SPU 删除无约束** | 标注 TODO，未实现 | 同上 |
| 5 | **报价区间不允许重叠** | 生效日期不能与已有生效报价重叠，但业务可能需要灵活覆盖 | 用户操作受限 |
| 6 | **SKU 助记码无法修改** | 新增后助记码写死，改名称后助记码不同步 | 数据不一致 |
| 7 | **SKU 导入无去重** | 与 SPU 不同，SKU 导入没有同客户+同名+同单位的去重保护 | 可能重复导入 |
| 8 | **取价未命中返回空** | 三层均未命中时返回空价，录单时需手动补价 | 用户体验差 |
| 9 | **报价明细全量替换** | 修改报价单时先 DELETE 全部明细再 INSERT，无增量更新 | 审计追踪困难 |
| 10 | **配送点 location 字段未用** | 数据库定义为 GEOMETRY，实体类为 String，无实际使用场景 | 无用字段 |
| 11 | **SKU 编码含客户 ID** | 客户 ID 变更时 SKU 编码需要全量重生成 | 扩展性差 |
| 12 | **SKU 列表默认 customerId=0** | 前端默认查询 customerId=0 的 SKU，需先切换客户才能看到数据 | 新手引导缺失 |

### 12.3 数据流示例

```
[录单场景] 用户为某客户下单"西红柿"

1. 前端 GET /price/query?customerId=1&deliveryPointId=2&skuId=5&deliveryDate=2025-06-13
   ↓
2. 后端 PriceQueryService 按优先级取价：
   a. delivery_point_price: 查 delivery_point_id=2, sku_id=5, 日期在区间 → 找到 price=5.8
   b. 直接返回 PriceQueryResult(price=5.8, source=1)
   ↓
3. 前端将 price=5.8 展示在订单行上

---

[搜索场景] 用户输入"番茄"搜索商品

1. 前端 GET /product/sku/page?customerId=1&name=番茄
   ↓
2. 后端 SQL 同时匹配：
   - sku.name LIKE '%番茄%'           (无结果)
   - sku.mnemonic_code LIKE '%番茄%'  (无结果)
   - product_alias.alias LIKE '%番茄%'(命中: sku_id=5, alias="番茄")
   - customer_sku_mapping.customer_alias LIKE '%番茄%' (无结果)
   ↓
3. 返回 sku_id=5，并因其是别名匹配而优先排序
   ↓
4. 前端展示该 SKU 在列表首位
```
