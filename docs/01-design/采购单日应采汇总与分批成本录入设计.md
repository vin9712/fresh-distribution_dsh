# 采购单重设计：日应采汇总（送货单总表口径）+ 分批成本录入

> **状态**：🟢 设计定稿（2026-09-15 经用户确认，待开工）
> **一句话主张**：采购单不该是「一键生成一堆带销售价的应采行」，而应是**订单视图（当日应采清单）→ 文员按批次录数量与进货价 → 加权成本统计**。和 D-055 把送货单改成「订单的视图」同构：**应采清单是实时视图不落库，`purchase_item` 行 = 一次实际进货批次**。
> **关联**：D-055 送货单视图化（`送货单矩阵总表与批次视图设计.md` §十八/§十九）、[`客户日报表打印优化设计`](客户日报表打印优化设计.md)、`OrderWithdrawCascadeServiceImpl`（W0-2.1 撤回级联）、W0-2.5 已确认采购纠错、W0-3.1 月结冻结、W0-3.3 经营概览。
> **决策编号**：本文使用 **D-056 ~ D-063**（承接 D-055，不占用 PT-x 序列）。

## 一、背景：现状采购单为什么不好用（2026-09-15 查实）

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| P1 | **一键生成的是「应采行 + 销售价」**：`selectSummaryByDeliveryDate` 取 `min(d.product_price)` 当采购单价 | `PurchaseItemMapper.xml:107-141` | 生成出来的「采购总额」是**卖价乘应送量**，不是成本；文员必须逐行改价才能用，等于生成了 95% 的废数据 |
| P2 | **不支持分批**：一行一个 SKU，`updatePurchase` 先删后插 | `PurchaseOrderServiceImpl.updatePurchase` | 生鲜当天常分多次/多供应商进货、每次价不同；只能录成一个加权价，或反复改单，成本不可追溯 |
| P3 | **数量只能录「应送量」**：`quantity = SUM(num)` | 同 P1 | 实际采购量与应送量必然有差（损耗/多进/少进），现状没有「应采 vs 已采 vs 待采」对照 |
| P4 | **商品可自由录入**：`createPurchase` 只校验明细非空，SKU 来自全量 `listSku()` | `PurchaseOrderServiceImpl.createPurchase` / `views/purchase/index.vue` | 违背「采购商品必须是订单商品」；成本与销售对不上，报表口径失真 |
| P5 | **录入界面是弹窗表单**，无当日全局视图 | `views/purchase/index.vue`（920px dialog） | 文员看不到「今天一共要买什么、录了多少、还差多少」，只能盲录 |
| P6 | 供应商只在单头，一天多供应商要拆单 | `purchase_order.supplier_name` | 与 P2 冲突；改成同一供应商拆单又会破坏「一天一单」的成本归集 |

> 结论：现有 `generate*` 生成口径（应送量 × 卖价）必须**废弃语义**，改为「应采清单只读视图 + 批次录入写入 `purchase_item`」。

## 二、总体方案（与 D-055 送货单视图化同构）

```text
                    ┌──────────────────────────────────────────┐
   t_sale_order ───► │  应采清单（实时视图，不落库）               │
   t_sale_order_detail│  按「采购汇总键」GROUP BY SUM(num)        │
   （status>=1）      │  key = sku + 品名 + 规格 + 单位            │
                    └──────────────────┬───────────────────────┘
                                       │ 页面锚点：当天的送货单总表（采购口径）
                                       ▼
   ┌──────────────────────────────────────────────────────────────┐
   │  采购单（purchase_order，一天一单，order_date = 配送日期）      │
   │  ┌────────────────────────────────────────────────────────┐  │
   │  │ purchase_item 行 = 一次实际进货「批次」                  │  │
   │  │   sku + 品名/规格/单位快照 + 数量 + 进货价 + 小计          │  │
   │  │   + 批次序号 batch_no + 批次供应商 + 录入人/录入时间       │  │
   │  └────────────────────────────────────────────────────────┘  │
   └──────────────────────────────────────────────────────────────┘
                                       │
                    ┌──────────────────┴───────────────────────┐
                    ▼                                          ▼
          行统计（视图计算）                          成本统计
   已采=Σ批次数量 · 待采=应采−已采                  加权均价=Σ小计/Σ数量
   批次数 · 采购金额                              日采购额 · 经营概览 · 月结
```

**三条不变量**：

1. **应采清单是视图**：永远由订单明细实时算出，不写入采购表；订单撤回/加单后自动变化（对齐 D-055「送货单=订单的视图」）。
2. **采购行是事实**：`purchase_item` 只记「真的买了什么、多少钱」，一行 = 一个批次，不做产品目录。
3. **商品必须在订单里**：批次行的商品键必须命中当日应采清单，否则拒绝（见 §六）。

## 三、应采清单数据源（「当天的送货单总表」采购口径）

行 = 采购汇总键（与 `OrderWithdrawCascadeServiceImpl` 的扣除键、`selectSummaryByOrderIds` 的 group by **完全一致**，保证级联能对上）：

```sql
select d.sku_id,
       d.product_name,
       d.product_spec,
       d.product_unit,
       sum(d.num) as required_qty          -- 应采数量
from t_sale_order_detail d
join t_sale_order o on o.id = d.order_id
where o.delivery_date = #{orderDate}
  and o.status >= 1                        -- 非草稿即应送；退货行 num 已归 0
  and o.is_deleted = 0
  and d.is_deleted = 0
group by d.sku_id, d.product_name, d.product_spec, d.product_unit
having sum(d.num) > 0                       -- 全为 0 的纯退货组不进清单
order by d.sku_id, d.product_name
```

- **读口径 `o.status >= 1`**（对齐 D-055 §十九.1）：验收后订单进入 `ACCEPTED(3)` 时清单不消失，当天采购页可回看。
- **写口径**不变：验收创建仍只取 `status = 1`。
- 若某 SKU 的全部订单被撤回 → 清单行消失，但已录批次仍要在页面上可见（标「订单已撤回」），见 §六.4。

## 四、数据模型

### 4.1 `purchase_item`：从「应采行」改为「进货批次行」

```sql
ALTER TABLE purchase_item
  ADD COLUMN batch_no      int          NOT NULL DEFAULT 1  COMMENT '同商品组内批次序号（1,2,3…）' AFTER purchase_id,
  ADD COLUMN supplier_id   bigint                DEFAULT NULL COMMENT '本批次供应商ID（可空）'      AFTER sku_id,
  ADD COLUMN supplier_name varchar(200)          DEFAULT NULL COMMENT '本批次供应商名称（直填）'    AFTER supplier_id,
  ADD COLUMN required_qty  decimal(12,2)         DEFAULT NULL COMMENT '录入时快照的应采数量（差异审计用）' AFTER quantity,
  ADD COLUMN create_by     varchar(64)           DEFAULT ''   COMMENT '录入人'                   AFTER sort,
  ADD COLUMN create_time   datetime              DEFAULT NULL COMMENT '录入时间'                  AFTER create_by,
  ADD COLUMN remark        varchar(500)          DEFAULT NULL COMMENT '批次备注（发票号/车次等）' AFTER create_time;
```

- `unit_price` 语义从「销售价占位」正式定为 **进货成本价**。
- 同一 `sku + 品名 + 规格 + 单位` 允许 N 行，`sort` 管显示顺序，`batch_no` 管批次序号。
- 快照字段（品名/规格/单位）由**后端从应采清单回填**，不接受前端传值。

### 4.2 `purchase_order`：语义收敛，不新增列

| 列 | 现状 | 新语义 |
|---|---|---|
| `order_date` | 采购归属日期 | **采购日期 = 订单配送日期**，一天一单（服务端 get-or-create 幂等） |
| `source_type` | 1 自动生成 / 2 手工创建 | **删除**（开发期清库重构）：唯一主路径 = 按日应采汇总，手工建单退役，无需再区分来源 |
| `source_order_ids` | 来源订单 JSON | **删除**：视图化后撤回级联改按 `order_date` 反查当日采购单（§十），不再需要 JSON 引用 |
| `supplier_name` / `purchaser` | 单头供应商 | 保留为**默认供应商/采购员**；真正的供应商挂在批次行（可空，回落单头） |
| `total_amount` | 生成时算一次 | **每次批次增删改实时重算** = Σ `purchase_item.subtotal` |
| `status` | 0草稿/1已确认/2已入库/3已作废 | 语义细化见 §五 |

### 4.3 新建 SQL 脚本（`sql/s30_purchase_batch_entry.sql`）

用户已确认「开发中，历史采购数据可全清、表结构可改」，因此脚本分两段（对齐 `s23` 的 A/B 段约定）：

- **A 段（幂等 DDL，必执行）**：`information_schema` 探测后 `ALTER` 加批次列（§4.1）；`purchase_order` 删 `source_type` / `source_order_ids` 两列；同步 `sql/init_all.sql` 建表语句与 ALTER 区。
- **B 段（数据清理，注释保护，人工确认后执行）**：
  ```sql
  -- DELETE FROM purchase_modify_log;
  -- DELETE FROM purchase_item;
  -- DELETE FROM purchase_order;
  ```
  清空后旧「应送量 × 销售价」脏数据不再进入统计；如需重置单号序列，由 `biz_code_seq` 按日期自然重置，无需额外处理。

> **开发期优势**：因为可清库，不需要为旧语义写迁移/纠价脚本，`purchase_item` 直接按目标结构落地即可。

## 五、状态机与操作边界

```text
0 草稿（录入中） ──确认──► 1 已确认（成本待确认） ──入库──► 2 已入库（成本已确认）
     │                              │
     └──── 空单/撤回级联 ──► 3 已作废（终态，只读）
```

| 状态 | 别名（页面文案） | 批次行 | 单头 |
|---|---|---|---|
| 0 | 录入中 | 可**增/删/改**批次（分批录入的主战场） | 可改默认供应商/采购员/备注 |
| 1 | 成本待确认 | 禁止增删；可「调整成本」改数量/单价（W0-2.5，写 `purchase_modify_log` 审计） | 可供应商补录 |
| 2 | 成本已确认 | 冻结 | 冻结；月结后走下月调整单（TJ） |
| 3 | 已作废 | 只读 | 只读（不可确认/入库/删除） |

- 单测/报表口径沿用：待确认成本 = `status in (0,1)`，已确认成本 = `status = 2`，采购额排除 `status = 3`。
- **超采与确认**：超采仅页面提示，`confirm` 不做「录齐/未超采」校验（D-062：不影响下单与验收）。
- 月结冻结按 `order_date` 归月（沿用 W0-3.1）。

## 六、校验规则（「选的商品必须要是订单商品里有的」）

### 6.1 录入批次（`POST /purchase/{id}/batch`）

1. **商品命中校验**：`skuId`（临时商品按 `品名+规格+单位`）必须命中当日应采清单；否则 `ServiceException("商品【X】不在当日订单商品内，不可录入采购")`。
2. **快照回填**：品名/规格/单位一律取应采清单值，忽略请求体。
3. `quantity > 0`、`unitPrice >= 0`；`subtotal = round(quantity × unitPrice, 2)` 服务端算，忽略前端。
4. 非草稿状态拒绝写入（已确认走调整接口）。

### 6.2 批量录入（`POST /purchase/batch-bulk`）

逐行执行 §6.1，**任一行非法整体回滚**（与 `batchStockIn` 同风格），返回成功行数。

### 6.3 应采清单的商品选择器

前端「批量录入」的商品下拉只加载 `GET /purchase/day-summary` 返回的行（当日订单商品），**不调用全量 `listSku()`**；后端仍做 §6.1 兜底。

### 6.4 订单撤回后的遗留批次

应采清单收缩后，若已有批次对应的商品不再在清单里：页面保留该行并标红「订单已撤回（应采 0）」，不自动删除批次（成本是事实），由文员确认后走撤回级联或手工删批次（仅草稿）。

## 七、成本统计口径

| 指标 | 口径 | 计算位置 |
|---|---|---|
| 行已采数量 | `Σ quantity`（该采购汇总键全部批次） | 视图/SQL |
| 行待采数量 | `应采 − 已采`（**可为负**=超采，标红） | 视图/SQL |
| 行加权平均进价 | `Σsubtotal ÷ Σquantity`（显示 4 位小数，避免「均价×数量≠金额」） | 视图/SQL |
| 行采购金额 | `Σsubtotal` | 视图/SQL |
| 日采购总额 | `purchase_order.total_amount`（= Σ所有批次小计，实时重算） | 服务端 |
| 日应采品种完成度 | 已录品种数 / 应采品种数；已采总数量 / 应采总数量 | 视图 |
| 经营概览 / 月结 | **不变**：按 `order_date` 归期，排除作废单；`待确认成本 = status in (0,1)` | 既有 `ReportMapper` |

> **本期范围收敛（用户 2026-09-15 确认）**：参考进价（最近价）**暂不做**；采购单**只做「录入 + 统计」**，不做采购单打印、供应商对账单、库存入库对账。超采**允许**且**不影响下单与验收**（JIT 之外的库存冗余属正常）。

> 「不做订单级成本分摊」的蓝图边界不变（蓝图 line 24/34）：成本只到 SKU × 日期，不拆分回销售订单。

### 9.2 录入交互

- **单行录入**：行尾「+ 录入」→ 小对话框（数量 / 进货价 / 供应商 / 备注 / 小计预览），**商品锁定为该行**（天然保证在订单商品内）；保存后可「继续录下一批」。
- **批量录入**：顶部「批量录入」抽屉，表格可加行；商品下拉**只含当日应采清单**（`filterable`，同一商品可重复选以录不同批次），一次提交多行；提交前本地校验数量/单价。
- **实时反馈**：录入后立即刷新该行 已采/待采/均价/金额 与顶部统计，无需整页刷新。
- **超采提示（允许、不阻断）**：待采为负 → 行标红 + 顶部告警「N 行已超采」，但**不拦截确认、不影响下单与验收**（D-062）。
- **未录齐提示**：顶部显示「还有 N 个品种未录满」，确认时仅提示不拦截（确认后批次不可增删）。

## 十、撤回级联的批次化改造（W0-2.1）

现有 `OrderWithdrawCascadeServiceImpl` 靠 `source_order_ids` JSON 找到采购单、再按采购汇总键扣减**单行**数量。视图化后 `source_order_ids` 删除，改为**按日期反查**：

```text
1. 取被撤回订单的 delivery_date = D
2. 反查 D 当日「非作废」采购单（latest by id，最多 1 张，覆盖作废后重建场景）
   若无 → 无事可做
3. 把被撤回订单的有效明细按「采购汇总键」聚合，作为应扣量
4. 对每个键：取出当日采购单该键下全部批次行，按 id 倒序（后录入的先扣）
   逐行扣 min(剩余应扣, 行数量)，扣至 0 删行；扣不完的（超扣）钳零删行
5. 重算 purchase_order.total_amount；无明细 → 自动作废（原因「订单撤回」，沿用 VOIDED）
6. 拒撤线：仍为「被已入库（STOCKED）采购单引用」即拒撤（不变）
```

- **无需 JSON 引用即可精确定位**：一天一单 + `order_date` 是唯一入口，比 JSON 更抗「采购单事后手工增删明细」（现状 JSON 会与实际明细不一致）。
- 单批次行为与现状完全一致（等价于只有一行）。
- 新增单测覆盖：按日期反查、多批次分摊扣除、跨批次扣净删行、部分扣除保留行、空单作废、已入库拒撤、作废后重建单。

> **超采与撤回的关系**：因为超采允许，撤回扣减仍按「被撤订单贡献量」扣、扣不足钳零，**不会因为存在冗余库存而拒绝撤回**；冗余部分留在采购单里继续计入成本统计。

## 十四、已确认结论（2026-09-15）

| # | 问题 | 结论 | 对设计的影响 |
|---|---|---|---|
| 1 | 供应商粒度 | **批次级**，同一供应商同一天可录多次 | D-057 保持；不做「一天一供应商一单」，单头供应商降为录入默认值 |
| 2 | 超采 | **允许**（JIT + 库存冗余），不影响下单与验收 | D-062 改为「允许、不阻断，仅标红提示」，**删除确认时的二次确认/硬拦逻辑** |
| 3 | 历史采购单 | **可全清**（开发中，表结构可改） | §四.3 增 B 段清理脚本；退役 `source_type`/`source_order_ids`，无迁移/纠价脚本 |
| 4 | 参考进价 | 选**最近价**，但**系统暂用不上** | 本期不做；采购页只保留「录入 + 成本统计」，§十一 P1/P2 已收敛为「明确不做」 |

> 至此无阻塞性待确认项。开工前唯一待定：`/purchase/cost-stat` 统计页是**独立页**还是**只做日录入页顶部统计条**（建议先只做统计条，够用再拆页）。
