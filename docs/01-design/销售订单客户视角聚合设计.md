# 销售订单客户视角聚合设计

> **状态**：🟢 已落地（2026-09-19 设计定稿并实施；决策 **D-064 ~ D-068** 全部已确认），承接基线《[销售订单与送货单关系设计](../销售订单与送货单关系设计.md)》D-001~D-037、《[送货单客户维度设计](送货单客户维度设计.md)》D-038~D-042、《[送货单矩阵总表与批次视图设计](送货单矩阵总表与批次视图设计.md)》D-043~D-055。
>
> **一句话主张**：销售订单页的第一维度是**客户（+ 配送日期）**，不是配送点、不是订单。配送点多时列表必须**折叠到客户行**，明细单（一行 = 一个配送点的订单）在**行内二层展开**里查看与操作，菜品级明细仍进订单明细页。

---

## 一、问题：为什么现在会臃肿

| 事实 | 出处 | 推论 |
|---|---|---|
| 一张销售订单 = 一个客户 + 一个配送点 + 一个配送日期（`customer_dept_id` 可空但录单时必选） | `t_sale_order` / `sale/detail.vue` | 客户有 N 个配送点 → 一天 N 张订单 |
| 列表当前一行 = 一张订单（`selectSaleOrderList` 平铺，无分组） | `SaleOrderMapper.xml` | 20 个点的客户 = 20 行，翻三页都是同一客户 |
| 下游全部按「客户 + 日期」收敛（客户日报表 / 矩阵 / 配货 / 点单 / 验收） | D-038、D-043、D-055 | 文员的**处理单元**是客户，列表的**展示单元**却还是订单 → 粒度错位 |
| 送货单据页已经用「主行 = 客户 + 配送日期，展开 = 子单」解决同类问题 | D-043 / `order/delivery/index.vue` | 有现成范式可对齐，不需要发明新交互 |

**结论**：订单是原料，配送点是分组，**客户才是文员的操作对象**。列表要能"一眼看清今天每个客户什么进度、还有哪些单要处理"，而不是把同一客户的 20 个点平铺出来。

---

## 二、三层信息模型（客户视角）

```text
L1 客户行（主行，一页 N 行）      客户 + 配送日期        ← 进度/金额/待办，整组批量动作
      │ 行内展开（懒加载）
L2 订单行（明细单）               + 配送点 + 班次        ← 单号/状态/金额 + 逐单操作（撤回/验收/结算/变更/删除）
      │ 点击单号 / 双击
L3 菜品行                       订单明细页（现有）      ← 菜品/数量/单价/小计，不在列表页展开
```

- **L1 是新增**：聚合视图，只读汇总 + 组级动作。
- **L2 是现有列表的降级复用**：字段与操作**完全沿用**现有 `sale/index.vue` 行内容，不新增业务动作、不改接口语义。
- **L3 不动**：菜品级查看/编辑仍走 `/order/sale-detail/index?orderId=`，避免列表页背菜品明细的性能与交互负担。

> 与 D-043 的唯一差别：送货单批次是**数据库里真实存在的分组**（`t_delivery_batch`）；销售订单的客户行是**查询期聚合**，不落库、不加表。

## 三、L1 客户行字段设计

| 列 | 内容 | 说明 |
|---|---|---|
| 展开 | `type="expand"` | 懒加载该客户当日订单子行 |
| 客户 | `coalesce(alias, name)` | 与全站口径一致 |
| 配送日期 | `delivery_date` | 分组键之一 |
| 张数 / 点数 | `orderCount` / `pointCount` | 张数带 badge，点数 = `count(distinct customer_dept_id)` |
| 进度分布 | `草稿 x · 已确认 x · 已配送 x · 已验收 x · 已结算 x` | 只显示非 0 项；**草稿/已配送/已验收分别对应待确认/待验收/待结算**，用颜色提示待办 |
| 合计金额 | `sum(amount)` | 分组内 Σ |
| 操作 | 整客户动作（见 §五） | 组级，作用于该客户当日全部订单 |

> **班次不进主行**（2026-09-19 确认）：班次是「订单级」属性，只有启用班次的客户才需要区分，主行加列会对绝大多数客户显示空值。班次仅在 **L2 子行**展示（未启用班次的客户子行显示 `—`）。

**明确不做**（保持主查询轻量）：

- 不在主行做 `allocated`（撤回占用）/ 验收单存在性 / 采购单号 / 送货单号——这些是**逐单**判断，且现有实现是相关子查询（`selectSaleOrderVo` 里 3 个），放大到 `group by` 会显著拖慢。它们全部下沉到 L2 子行（子行复用现有 SQL，口径零漂移）。
- 不在主行展开菜品。

## 四、后端：分组聚合分页

### 4.1 为什么必须后端分组

前端分组会**切断同一客户**：第 1 页最后一行与第 2 页第一行可能是同一客户。与 D-043 同理，分组必须在 SQL 层完成，分页单位 = 客户行。

### 4.2 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/order/sale/customer-page` | `order:sale:list` | **新增**：客户维度聚合分页（复用 `startPage()`，分页单位 = 客户行） |
| GET | `/order/sale/list` | `order:sale:list` | **既有，不改**：L2 子行数据源，展开时带 `customerId + deliveryDate`（+ 当前筛选条件）调用 |
| GET | `/order/sale/page` | `order:sale:list` | **既有，不改**：明细视角（平铺）继续使用 |

### 4.3 `SaleCustomerPageVO`（新增）

```text
customerId, customerName, deliveryDate,
orderCount, pointCount, totalAmount,
draftCount, confirmedCount, deliveredCount, acceptedCount, settledCount
```

### 4.4 SQL 要点（`SaleOrderMapper.xml#selectCustomerPage`）

```sql
select so.customer_id                       as customerId,
       coalesce(c.alias, c.name)            as customerName,
       so.delivery_date                     as deliveryDate,
       count(*)                             as orderCount,
       count(distinct so.customer_dept_id)  as pointCount,
       coalesce(sum(so.amount), 0)          as totalAmount,
       sum(case when so.status = 0 then 1 else 0 end) as draftCount,
       sum(case when so.status = 1 then 1 else 0 end) as confirmedCount,
       sum(case when so.status = 2 then 1 else 0 end) as deliveredCount,
       sum(case when so.status = 3 then 1 else 0 end) as acceptedCount,
       sum(case when so.status = 4 then 1 else 0 end) as settledCount
from t_sale_order so
left join t_customer c on c.id = so.customer_id
where so.is_deleted = 0
  -- 复用现有筛选：customerIds / customerDeptIds / customerDeptId / status / deliveryDate / code ...
group by so.customer_id, coalesce(c.alias, c.name), so.delivery_date
order by max(so.create_time) desc, max(so.id) desc
```

- **不复用 `selectSaleOrderVo`**：新建精简 SQL，避免把 3 个相关子查询带进分组。
- 筛选条件与现有 `selectSaleOrderList` **逐条对齐**（含 `customerDeptIds` 多选），保证"筛选后数字"与明细视角一致。
- 服务层无需补字段（班次不进主行），实现为 Mapper 直出。

### 4.5 L2 子行加载

复用 `GET /order/sale/list`，前端展开时传：

```text
customerId + deliveryDate + 当前 status / code / customerDeptIds 筛选
```

与 D-043 的 `loadBatchChildren` 完全同构（`__loaded` / `__loading` 标记 + 前端缓存，避免重复请求）。子行排序建议在 SQL 里加 `customer_dept_id asc`（一期可不做，沿用 `create_time desc`）。

> ⚠️ **字段名不能用 `children`**（2026-09-19 实测踩坑）：el-table 会把带 `children` 数组的行识别为**树形数据**（`childrenColumnName` 默认 `children`），在展开列尚未注册的渲染时机走树形渲染分支，对子行调 `getRowIdentity` 时抛 `For nested data item, row-key is required`（页面报错、表格渲染中断）。客户行的子单集合字段命名为 **`orders`**（`src/views/order/sale/index.vue`）。

## 五、交互设计

### 5.1 视图切换（D-066）

工具栏右侧加 `el-radio-group`（客户视角 / 明细视角）：

- **默认客户视角**；选择写 `localStorage`（键 `sale:listView`），下次进入沿用。
- **按订单编号搜索时自动切明细视角**：客户视角下 `code` 过滤的语义是"该客户当天有这张单"，用户看到的却是一整行客户，认知成本高。自动切换 + 顶部一条可关闭提示（"已按单号切换明细视角"）。
- 两个视角共用同一套筛选表单与 `queryParams`。

### 5.2 展开与子行（D-065）

- 展开 **懒加载**，加载中显示 `v-loading`；已加载不重复请求。
- 子行字段与操作**沿用现状**（订单编号 / 配送点 / 班次 / 金额 / 状态 / 备注 / 撤回 / 去验收 / 查看验收 / 撤回验收 / 结算 / 配送后变更 / 修改 / 删除 / 调整摘要），`v-hasPermi` 原样保留。
- **`orderCount === 1` 的客户默认自动展开**（无聚合价值，少一次点击）；可在工具栏用开关关闭。
- `customer_dept_id` 为空的订单子行显示「未指定配送点」（不隐藏、不合并）。
- 主行点击**不跳转**，双击主行 = 展开/收起；双击子行 = 进订单明细页（沿用现有 `handleRowDblClick`）。

### 5.3 批量与选择（D-067）

选择权**下沉到 L2 订单行**（批量确认/月结/还原/删除的语义本来就是订单级）：

- 勾选在子行；批量条显示 `已选 N 张订单 · 覆盖 M 个客户`。
- 跨多个客户展开后勾选，选择结果**累计**（不因收起而丢失）。
- 主行提供**整组动作**（作用于该客户当日全部订单）：
  - `确认草稿（x）`：仅当 `draftCount > 0`，二次确认列出"将确认 N 张"，任一订单状态不符时**整体不执行**（沿用现有 `handleOrderApproval` 校验口径）。
  - `批量月结`：仅当 `acceptedCount > 0` 且具 `order:sale:settle` 权限。
  - `导出该客户`：可选，一期不做。
- **不做**"一键删除整客户"（破坏性太强，只允许逐单/勾选删除）。

### 5.4 筛选语义（D-068）

- 客户视角下 `status` 筛选 = "该客户当日**存在**该状态的订单"（`WHERE` 生效，不是 `HAVING`）；主行进度分布仍展示**全部状态计数**，并在主行标一个「筛选中」小标，避免"筛了已配送却看到草稿数"的误读。
- `配送日期` 不填时不限日期，此时一行 = 一个客户的**一天**（同一客户多天 = 多行）——这是分组键的必然结果，也是刻意的：跨日期合并会让"确认/结算/验收"失去时间锚点。
- 工作台跳转携带的 `status` 路由参数照常生效（`activated()` 逻辑不变）。
- 草稿恢复横幅、`keep-alive` 自动刷新逻辑**保持不变**。

## 九、风险与取舍

| 风险 | 取舍 |
|---|---|
| 分组键含日期 → 同一客户多天出现多行，用户可能觉得"没完全合并" | 有意为之：确认/验收/结算都锚定配送日期；跨日期合并会让操作失去语义。默认筛选常带日期，实际很少看到多行 |
| 主行不做 `allocated`/验收判断 → 主行的"可撤回/待验收"只能是近似 | 精确判断留在子行（口径零漂移），主行只用状态分布近似表达待办，不做承诺式文案 |
| 两个视角 = 两套表格模板，维护成本 | 子行直接复用现有列与操作模板，主行只新增聚合列；筛选/权限/草稿横幅全部共用 |
| 按数据出列 → 各客户子表列不一致，可能让人以为"少了列" | 只在**空列**（班次/备注）上做，且标题行显式写明"N 张订单"；有数据即出列，不会丢信息 |
| `group by` + `startPage()` 的 count 查询 | 已核实 PageHelper 6.1.0 对 `group by` 包一层子查询计数（= 客户行数），非订单数；分组 SQL 已对真实库验证 |
