## 〇、一句话定位

**验收的「交互」回归订单明细页：订单已配送后，从订单列表点「去验收」，打开的就是订单明细本身——左侧下单数据只读锁定，右侧选单区隐藏，新增可编辑「实收数量」列与行级「换货/退货/加单」操作，顶部「一键验收」整单确认。数据的「载体」仍保留验收单（审计/撤销/退货引用/结算依据不变），仅维度从「客户+日」改为「订单」。**

## 一、与既有两版设计的关系（为什么这么收敛）

| 版本 | 交互 | 数据载体 | 结果 |
|---|---|---|---|
| 2026-02 方案A | 订单页录实收 | 无验收单，实收直接落 `t_sale_order_detail.actual_*` | 已定稿但未实施 |
| 2026-09 现行（AC-x） | 验收页弹窗录入 | 验收单（客户+日一单），明细行=订单明细行 | **已实施** |
| 本设计（OA） | **订单明细页验收（本设计）** | 验收单（**订单一单一验**） | 交互采纳方案A，载体保留 AC-x |

理由：

1. **退货单（D-032）按 `acceptance_item` 行级引用、月结以验收总额为结算依据、撤销有完整审计快照**——这些已建成的底座全部依赖验收单存在；纯方案A（落订单字段）要把退货引用、结算取数、撤销审计全部重做，改动面大且第三次反转口径。
2. 现行验收单的「明细行=订单明细行」模型（D-055 后）与订单明细页天然同构，把录入界面从弹窗搬到订单页只是**视图层搬家**，服务层逻辑大部分复用。
3. 维度从「客户+日」改为「订单」的原因：入口和心智都是「这张订单验没验」，一张客户日验收单混多张订单的行，在订单视角页面里会出现「别人的行」，且一键验收的「按订单数量金额批量处理」语义只有订单维度才干净。客户日级别的汇总诉求由客户日报表/总表承接（见 OA-7）。

## 二、链路总览

### 2.1 状态机（订单）

```
草稿0 → 已确认1 ──(送货单送达)──> 【可验收】──一键验收/逐行验收+提交──> 已验收3 → 已结算4
                │                                                    │
                └── 撤销验收（acceptance:revoke，原因必填）<───────────┘ 回到【可验收】
                            （任一来源订单已月结则拒绝撤销，复用现行守卫）
```

- 订单自身状态机不变（0/1/2/3/4）。新流程订单在验收前停在 `已确认(1)`（D-055 口径，DELIVERED 由送货单承载）；历史单停在 `已配送(2)`。两种状态都视为「可验收」，入口统一。
- 验收单状态机不变：`草稿0 → 已提交1`，撤销回到草稿。

### 2.2 链路泳道

```
文员                订单列表页                订单明细页(验收模式)              后端
 │  见 status∈{1,2}    │                            │                        │
 │──点「去验收」──────>│                            │                        │
 │                     │──GET /acceptance/by-order─>│                        │
 │                     │<─{acceptanceId?|null}──────│                        │
 │                     │──router.push──────────────>│                        │
 │                     │   /order/sale-detail?mode=acceptance&orderId=xxx    │
 │                                                  │──GET 订单+明细(快照)──>│
 │                                                  │──GET/建 验收草稿──────>│ create-by-order(无单时)
 │  逐行录实收/标换退加                               │<─合并视图行────────────│
 │─────────────────────────────────────────────────>│                        │
 │                                                  │──(防抖)保存草稿───────>│ PUT /acceptance
 │  或点「一键验收」                                  │                        │
 │─────────────────────────────────────────────────>│──POST quick-accept───>│ 原子:建单+录行+提交
 │                                                  │<─OK,订单已验收──────── │ +回写actual_*镜像
 │  已验收态:只读/撤销                                │                        │ +订单→ACCEPTED
```

## 三、入口与路由（OA-1）

### 3.1 订单列表入口

- 「去验收」按钮显示条件：`status ∈ {1, 2}`（现状代码只有 `status==2`，需放开到 1；status=1 时后端校验该订单所在客户日送货单是否已送达，未送达则 toast「尚未送达，送达后才能验收」——复用 `locateAcceptanceByOrder` 的校验能力）。
- `status=3/4`：按钮变为「验收单」（只读查看，仍进本页面，自动只读态）。
- 点击行为：`locateAcceptanceByOrder(orderId)` → 有验收单带 `acceptanceId` 直开；无则带 `create=1` 进入（页面挂载后自动建草稿）。

### 3.2 路由与组件复用

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 同组件加模式（推荐）** | `/order/sale-detail` 增加 `mode=acceptance` 查询参数，`detail.vue` 挂载时进入验收模式分支 | 改造集中、订单加载/快照/权限逻辑全复用；代价是 detail.vue（3200+行）继续膨胀 |
| B. 新建 `acceptance/detail.vue` | 抽取订单明细表格为公共组件后新建页面 | 结构最干净，但抽组件是一次性大重构，风险高 |

采用 A，并把「抽公共明细表格组件」记入技术债（§八）。验收模式下组件行为差异见 §四。

- **右侧选单区（常用/最近/搜索）整体不渲染**：验收模式跳过 `split-workspace`，表格占满全宽（或保留右侧放验收摘要卡，默认折叠，v1 不做）。

- 原有「实收数量/差异原因」镜像列（`showActualColumns`）在验收模式下由可编辑列接管，不重复显示。

### 4.2 列规格

| 列 | 来源 | 验收模式行为 |
|---|---|---|
| 商品/单位/规格/备注 | 订单明细快照 | 只读 |
| 下单数量 `num` | 订单明细快照 | 只读（`checkTableActive` 对该列返回 false） |
| 下单价 `productPrice` / 下单金额 | 订单明细快照 | 只读；手工定价「手」标签保留展示 |
| **实收数量** | `acceptance_item.actual_quantity`（草稿回显；无单时初始化=下单数量） | **可编辑** `vxe-input` 数字；加载即默认=下单数量（灰色待核），修改后行高亮为「已核对」 |
| 差异 | 前端算 `实收 − 下单` | ≠0 行黄底，负=红、正=橙；差异率超阈值（`sys_config acceptance.diff.warn.percent`，默认 ±20%）行红框，提交时弹确认不阻断 |
| 差异原因 | `reason_type` + `loss_reason`（字典 `acceptance_shortfall_reason`/`acceptance_overage_reason`） | 差异≠0 必填，选短收/超收对应字典；差异=0 置灰 |
| 实收金额 | `实收×下单价`（后端重算为准） | 只读，合计=验收总额（结算依据） |
| 变更标记 | `change_type`（1加单2换货3退货） | 行首 tag 展示；退货行下单数量/实收均显示 0、划线样式 |

### 4.3 数据加载与初始化

1. 挂载：解析 `mode=acceptance&orderId`，走既有「浏览历史单」加载路径拉订单+明细（天然只读快照，`checkSnapshotImmutable` 兜底）。
2. `by-order` 返回已有验收单 → 拉取 `acceptance_item` 按 `sale_order_detail_id` 合并回显实收/差异原因；状态=已提交 → 整页只读（§4.6）。
3. 无验收单且 `create=1` → 调 `create-by-order` 建草稿（应送行=该订单全部有效明细，含 D-055 标记行，退货行应送0实收0——复用 AC-2 规则，仅数据源从客户日改为单订单）。
4. 草稿已存在但订单明细后来新增了标记行（验收中途做了加单）→ 打开/保存时执行「同步缺失行」（服务端补插缺失的 `sale_order_detail_id` 行），不删旧行。

### 4.4 行级操作：换货 / 退货 / 加单（OA-3）

**完全复用 D-055 配送后变更链路（`SaleOrderDetailService` 标记接口），只是把入口从订单列表的 `saleChangeDrawer` 前移到验收页行内，点行级按钮时预填原明细行。**

| 动作 | 交互 | 落库效果 | 验收影响 |
|---|---|---|---|
| **退货** | 点行「退」→ 弹窗（预填原行，**整行退**，Q3 定稿 2026-09-09；部分退货走退货单 D-032）→ 确认 | 原行 `change_type=3`，应送/实收归 0 | 该行金额不计结算；实收列锁定 0 |
| **换货** | 点行「换」→ 弹窗选换入商品+数量+单价 | 原行标退货、新增换入行 `change_type=2`（同组） | 换入行按正常行验收（默认实收=应送） |
| **加单** | 点「加」（工具条或任意行后）→ 弹窗选商品+数量 | 该订单新增 `change_type=1` 行 | 新行出现在明细尾部，默认实收=应送 |

约束：

- 验收单**已提交**后行级操作禁用（按钮置灰 + 提示「请先撤销验收」）；订单已月结（status=4）同样禁用。
- 标记动作成功后：本地刷新该订单明细 → 触发 §4.3 第 4 步同步缺失行 → 新行以默认实收出现。
- 与订单列表入口的关系：~~`saleChangeDrawer`（订单列表「配送后变更」按钮）保留不动~~（2026-09-11 变更）订单列表「配送后变更」改为跳转订单明细页**变更模式**（`mode=change`，布局同验收模式：单栏明细表 + 行内加/退/换/回退，不渲染实收/差异列、不建验收单），`saleChangeDrawer.vue` 已删除；两处入口同源同效（同一套 D-055 接口）。

### 4.5 一键验收（OA-2）

位置：明细表格上方工具条最左（primary 主按钮）。

语义：**不做任何行级修改，按订单数量与金额整单确认**——全部行实收=下单数量、金额=下单金额，建单+录行+提交一步原子完成。

流程：

1. 点击 → 前端预检：逐行核对差异行；存在「差异≠0 但原因未填」→ 阻断并定位首行；存在超阈值差异行 → 弹窗列出供确认。
2. 确认弹窗：`应收 8 行 / ¥1,286.50 · 差异 1 行 / -¥12.00 · 实收合计 ¥1,274.50 · 验收日期 [默认今天]`，按钮「确认验收」。
3. 调用 **`POST /acceptance/quick-accept`**（原子接口，见 §五）：服务端完成 建单(若无)→写行→重算金额→提交→订单置已验收→回写 `actual_*` 镜像。
4. 成功 → 页面转已验收只读态，toast「订单已验收，验收单 YSxxx」；失败（并发/状态不符）→ 刷新页面到服务端真实状态。

配套按钮（同工具条）：

- **保存草稿**：手动保存当前实收与差异（`PUT /acceptance`），用于「录了一半改天再录」。
- **自动保存**：实收列编辑防抖 ~2s 静默保存草稿，横幅显示「已自动保存 HH:mm」（仅草稿态；对应 2026-02 方案 Q2 的防丢需求）。
- **提交验收**（可选保守路径）：与一键验收的差别仅在「不代填空值」——所有行已核对后提交；v1 可与一键验收合并为同一入口（一键验收本身就覆盖逐行确认后的提交）。

### 4.6 已验收态（只读视图）

- 横幅变绿：「订单已验收 · 验收单 YSxxx · 验收总额 ¥xxx · [查看验收单] [撤销验收] [返回订单列表]」。
- 实收列转只读展示，差异/原因照常显示；操作列隐藏。
- 「撤销验收」复用现行弹窗（原因必填、已结算拒撤、审计快照），成功后回到可编辑验收态。

### 4.7 权限与守卫

| 动作 | 权限 | 守卫 |
|---|---|---|
| 进入验收/查看 | `acceptance:query` | — |
| 录实收/存草稿 | `acceptance:edit` | 订单状态∈{1(已送达),2}；验收单为草稿 |
| 一键验收/提交 | `acceptance:submit` | 同上 + 差异原因完整 |
| 撤销 | `acceptance:revoke` | 非已结算；原因必填 |
| 行级换/退/加 | `order:sale:edit`（D-055 既有权限） | 验收单为草稿 |

并发：提交以验收单状态为闸（`status=0` 才可提交），双开页面后提交者后到者收到「验收单状态已变更」并刷新；不做行级锁。

## 五、数据模型与后端改动（OA-4 / OA-5）

### 5.1 表结构（最小 DDL）

```sql
-- acceptance 增加订单维度
ALTER TABLE acceptance ADD COLUMN sale_order_id BIGINT NULL COMMENT '订单维度验收：来源销售订单ID（历史单/客户日单为NULL）';
ALTER TABLE acceptance ADD UNIQUE KEY uk_sale_order (sale_order_id);
-- acceptance_item 已有 sale_order_detail_id，行=订单明细行，无需改动
```

- `acceptance.customer_id / delivery_date` 照旧填写（冗余存储，报表与守卫共用）；`delivery_point_id` 取订单配送点。
- 判定口径：`sale_order_id != null` = 订单维度新单；`= null` = 历史单/客户日单（只读兼容）。

### 5.2 服务层（`AcceptanceService`）

| 方法 | 说明 |
|---|---|
| `createByOrder(orderId)` | 新增。守卫：订单状态可验收 + `countBySaleOrder=0`；行构建复用 `createByCustomerDate` 的行逻辑，数据源换为「该订单的 `selectValidByCustomerDateForView` 等价查询（按 orderId 过滤）」；退货行应送0实收0、加单行默认实收取镜像（AC-2 规则原样继承） |
| `quickAccept(dto{orderId, acceptDate, remark, items[]})` | 新增。事务内：无单建单→覆写行（实收/原因/重算差异金额）→提交（复用 `submit` 的镜像回写与订单状态推进）→返回验收单号。任一环节失败整体回滚 |
| `syncMissingItems(acceptanceId, orderId)` | 新增。按订单当前有效明细补插验收单缺失行（验收中途加单场景），只插不删 |
| `locateBySaleOrder` | 调整为订单维度优先：`sale_order_id=orderId` 反查（客户日兜底查历史单，现有逻辑降级为回退分支） |
| `submit / revoke / update` | 不动（`deliveryOrderId==null` 分支天然适配；`submit` 的订单状态推进组=该订单自身） |
| `createByCustomerDate / createByDeliveryOrder` | 标 `@Deprecated` 注释保留：客户日总表与历史单入口暂存，观察期后随旧验收页下线（§七） |

### 5.3 接口清单（`AcceptanceController`）

| 接口 | 类型 | 说明 |
|---|---|---|
| `/acceptance/create-by-order` | POST | body `{orderId}`，perm `acceptance:add` |
| `/acceptance/quick-accept` | POST | §4.5，perm `acceptance:submit` |
| `/acceptance/by-order/{orderId}` | GET | 定位（现 `locateAcceptanceByOrder` 升级，返回 `acceptanceId/acceptanceStatus/orderView=true`） |
| `/acceptance/{id}/items` | GET | 现有，行回填 `orderCode` 已具备 |
| `/acceptance` PUT、`/{id}/submit`、`/{id}/revoke` | — | 现有复用 |

### 5.4 对既有引用的影响

- **退货单（D-032）**：仍引用 `acceptance_item`，行仍在，零改动。
- **月结**：结算取数按客户+验收日期聚合验收总额——订单维度单照常带 `customer_id/delivery_date`，报表口径不变；「一客户日多张验收单」在月结预览里体现为多行，金额合计一致（需在月结预览页确认展示无歧义，见 §八 测试）。
- **工作台「待验收」**：分组维度改为订单（`selectPendingAcceptance` 按 `sale_order_id` 判定），跳转改 `/order/sale-detail?mode=acceptance&orderId=`。
- **实收镜像**：`t_sale_order_detail.actual_*` 回写逻辑（1:1 镜像）不变，订单详情页 `showActualColumns` 展示逻辑不变。

## 六、边界与异常

| # | 场景 | 处理 |
|---|---|---|
| E1 | 一客户日多张订单 | 各订单独立验收、独立单号；客户日总表展示每单验收状态（§七）；先验收的订单先锁定 |
| E2 | 验收中途做加单/换货 | §4.4 同步缺失行；已录实收的行不丢（按 sale_order_detail_id 合并） |
| E3 | 整行拒收 | 实收填 0 → 差异=−下单数量 → 必填原因；无需标退货（标退货是「货没送/送错」的订单口径修正，影响应送） |
| E4 | 历史单（status=2，无客户日验收单） | 入口照旧走送货单反查兼容分支；本页只读打开或引导「历史单补建」 |
| E5 | 已进入月结期间撤销 | 复用现行守卫：任一来源订单 SETTLED → 拒绝撤销 |
| E6 | 验收单已提交，订单列表仍显示可验收 | 状态由 `by-order` 返回驱动按钮文案（已验收→「验收单」），提交后订单状态即时推 ACCEPTED，双保险 |
| E7 | 扫码枪/移动录入 | v1 不迁入本页（文员电脑录入为主）；现有验收页移动模式随旧页保留至下线评估 |
| E8 | 订单明细含临时商品/无 SKU | 行构建与实收录入不受影响（与现行客户日单同规则） |
