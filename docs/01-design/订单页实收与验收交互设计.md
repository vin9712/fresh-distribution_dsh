## 一、需求背景（来自一线使用反馈）

文员日常 80% 的工作是订单核对与验收。现状痛点：

1. **验收入口离数据太远**：验收单要从送货单另起一页创建，录实收时看不到原订单上下文，对照不便。
2. **两张表来回切**：核对"应收 vs 实收"需要在订单明细和验收明细两个页面之间跳转。
3. **流程重复**：大部分商品实收=应收，逐行填一遍纯属重复劳动。

## 二、目标方案（草案）

### 2.1 核心思想

**验收回归订单本身：在订单页直接录实收，原订单数据只读、实收追加在后。**

```
订单明细行（已配送状态下）
┌──────────┬───────┬────────┬────────┬────────┬──────────┐
│ 商品名称 │ 单位  │ 下单数量│ 下单价 │ 应收金额│ ★实收数量 │ ← 新增可编辑列
└──────────┴───────┴────────┴────────┴────────┴──────────┘
   只读，锁定      ↑ 订单处于 已配送(2) 状态前，此列不可见/禁用
```

- **下单数量/单价/金额**：已配送状态下全部只读（业务上此时改单无意义）。
- **实收数量**：仅 `status=已配送` 的订单显示可编辑列；默认值 = 下单数量。
- **一键验收**：列表页对已配送订单提供按钮——所有行默认实收=应收、无差异，直接置为已验收；有差异的行再单独改。
- **差异规则沿用现有校验**：实收 < 应收 时必须填损耗原因（复用 `AcceptanceServiceImpl` 现有逻辑）。

### 2.2 现状代码盘点（改造涉及面）

| 现状 | 说明 | 改造方向 |
|---|---|---|
| `t_sale_order_detail` 已有 `actual_num / actual_price / actual_amount` 列 | 与计划字段（num/product_price/expect_amount）并列，**表结构天然支持本方案** | 直接启用 |
| 验收独立成单：`acceptance` + `acceptance_item` 表 | 由送货单生成，submit 后按配送组把同组订单 DELIVERED→ACCEPTED（`AcceptanceServiceImpl.submit`） | 待决策：保留 or 废弃（见问题 Q4） |
| 验收页 `order/acceptance/index.vue` | 含移动模式（扫码枪连续扫码累加实收） | 待决策：是否迁移扫码能力到订单页 |
| 订单状态字典 `t_sale_order_status`：0草稿/1已确认/2已配送/3已验收/4已结算 | 已验收语义清晰 | 不变 |

## 三、问题确认记录

### 流程与权限

- **Q1 谁来验收？**
  ✅ **文员用电脑录**。目前没有仓配角色，移动端/扫码枪模式暂不需要。
- **Q2 批量验收的规则？**
  ✅ 提供「验收」按钮 + **多选批量验收**：
  - 实收数量为空 ⇒ 视为与下单数量一致；有记录的以记录为准
  - 实收与下单数相差较大（阈值 **±20%**，可配置）时弹出提示，人工二次确认后才提交
  - 录入过程要有**自动保存机制**（按订单号挂钩），防止误关网页丢失已填的实收数据
- **Q3 已验收填错怎么办？**
  ✅ 提供 **return（回退）机制**：「已验收」可退回「已配送」，重新填写；操作人是文员。

### 架构取舍

- **Q4 独立验收单去留？**
  ✅ **方案 A**。不存在传统意义上的验收单，所谓验收只是**订单内容上的一个验收确认动作**。`acceptance / acceptance_item` 表及独立验收页面后续退役。
- **Q5 加退换怎么衔接？**
  ✅ 加退换可以发生在验收环节，但**维持独立入口**，数据最终同步到订单明细，并在界面上做标识：
  - 新增行 → 备注标记「**加单**」
  - 删除行 → 显示**删除线**
  - 换货行 → 备注标记「**换货**"

### 交互细节

- **Q6 差异行的视觉呈现**：✅ 部分明确 —— ±20% 差异给提示；具体高亮/汇总条样式见 §4.2 建议，开发时可微调。
- **Q7 损耗原因的形式**：✅ 采用**固定字典**（如：挤压 / 破损 / 拒收 / 质量不达标 / 少送 …），后续按需扩充；统计损耗排行依赖此字典。
- **Q8 结算口径**：⏳ 未答复，列入 §4.6 待补项（当前实现默认实收金额即结算金额）。

## 四、定稿结论

### 4.1 总体架构

- **废弃独立验收单**（方案 A）。验收 = 在销售订单上的确认动作，实收数据直接落 `t_sale_order_detail.actual_num / actual_price / actual_amount`。
- 订单状态机不变：`草稿0 → 已确认1 → 已配送2 → 已验收3 → 已结算4`，新增一条迁移：**已验收 → 已配送（回退，文员操作）**。
- `acceptance / acceptance_item` 表、`/order/acceptance/**` 接口及前端验收页进入废弃清单（先停用菜单，观察一个调价周期后再删代码）。
- 工作台卡片「待验收」改为指向订单页（过滤 status=已配送），不再指向送货/验收页。

### 4.2 订单页交互规格

**明细区（订单状态=已配送 时激活）**

| 列 | 行为 |
|---|---|
| 下单数量 / 单价 / 金额 | 只读锁定 |
| 实收数量 | 可编辑输入框，默认空 = 取下单数；失焦或停止输入 ~1.5s 自动保存（防抖） |
| 损耗原因 | 仅当实收 < 下单数时必填，固定字典下拉 + 备注 |
| 差异标识 | 实收≠下单数的行黄色高亮；差异超 ±20%（sys_config 可配，默认 20%）的行红色高亮 + **仅弹出提示**（不阻断操作） |
| 明细底部汇总条 | 「本单 N 行有差异，合计多/少 X（单位）；超阈值 M 行」 |

**列表区**

- 勾选多条 status=已配送 的订单 → 点「**验收**」→ 批量确认弹窗：
  - 逐单展示：行数、空实收行数、有差异行数、超阈值行数
  - 空实收行自动按下单数计；超阈值行仅提示、不阻断，由文员自行判断后确认
  - 确认后整批置为「已验收」
- 单张订单也可在明细内直接点「确认验收」（等价于批量验收的单选特例）。

**自动保存**

- 按 `order_id` 维度暂存未确认的实收草稿（localStorage + 后端草稿字段双保险，优先后端）；
- 页面重开时检测到草稿则提示恢复；订单成功置为「已验收」后清除草稿。

### 4.3 回退机制

- 入口：已验收订单的操作列「**撤销验收**」（权限：文员及以上）。
- 动作：status 3→2，清空本次验收产生的 actual_* 值（或保留值但标记为可覆盖，开发取其一，默认**清空**）。
- 约束：若该订单已进入「已结算」或已被对账引用，禁止回退并给出提示。

### 4.4 加退换在验收环节的呈现

- 保持 OrderAdjustment 独立入口不变；同步规则不变（数据并入订单明细）。
- 明细行标识规范：
  - 加单行：行首 tag「加单」，备注列自动带「加单：xxx」
  - 删除行：整行删除线 + 置灰，不计金额
  - 换货行：tag「换货」，备注列自动带「换货：原商品→新商品」
- 验收确认时这些行一并随主单状态流转。

### 4.5 开发改造清单（建议顺序）

1. 后端：`SaleOrderDetail` 启用 actual_* 写入接口（批量保存草稿 / 批量确认验收 / 撤销验收 三个端点）+ ±20% 阈值提醒（sys_config 参数化，默认 20%，**仅提示非阻断**）
2. 后端：损耗原因字典 `biz_loss_reason` 初始化 SQL
3. 前端：订单详情页明细区改造（只读锁 + 实收列 + 自动保存 + 高亮/汇总条）
4. 前端：订单列表页多选验收按钮与确认弹窗
5. 前端：撤销验收入口 + 权限
6. 收尾：工作台卡片改指向、验收页菜单下线、manuals 同步更新（含《文员快速上手指南》§三.③）
