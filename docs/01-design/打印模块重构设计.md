# 打印模块重构设计（打印模板 2.0：单一事实来源 + 动态生成 + 真实数据预览）

> 状态：🟢 P0/P1/P2/P3/P4 已实施；P5 已评估（需业务确认后缓行）
> 目标：把「打印模板管理 + 积木报表维护」从**双层事实来源、SQL/脚本手工维护、静态样板导入**，
> 收敛为**单一事实来源、应用内物化、按当前数据契约动态生成、可用真实订单数据预览**的模型。
> 关联：`打印模板通用数据结构与模板设计.md`（数据契约）、`客户日报表打印优化设计.md`（PT-1~4 链路）、
> `送货单矩阵总表与批次视图设计.md`（D-055）、`docs/assets/print/hotels/README.md`（静态样板导入记录）。
> 决策编号：本文使用 **PR-x**（Print Refactor），不占用 D-0xx 序列。

---

## 〇、一句话结论

**把 `t_print_template` 变成打印模板的唯一事实来源，把 `jimu_report` 降级为「发布时物化出来的不可变渲染产物」，
把数据集/字段/参数的维护从 SQL 脚本搬进应用（物化器 + 数据契约），把静态样板导入换成从当前表结构动态生成骨架 +
真实订单数据预览。**

现状最大的问题不是「功能不够」，而是**同一份模板被存在两个地方、各说各话**：
业务绑定、状态、版本在 `t_print_template`，真正的版式在 `jimu_report.json_str`，
而 `t_print_template.content` 名义上是「模板内容(JSON)」、实际存的是 `jimu_report.id`。
这导致**版本回滚回滚不了版式、导入导出对真实模板直接报错、数据集必须靠脚本逐报表克隆**。

## 一、现状诊断（as-is）

### 1.1 对象与职责（现状）

| 对象 | 实际职责 | 问题 |
|---|---|---|
| `t_print_template` | 业务注册表：绑定（bind_type/customer/dept）、形态（print_form）、联数、状态机、版本号；`content` 存 `jimu_report.id` | `content` 命名与语义不符；`data`/`render_engine`/`type`/`is_deleted` 等字段事实弃用 |
| `t_print_template_version` | 版本快照：**只快照 `content`（报表ID）** | 版式存在 `jimu_report`，改版式不产生新报表ID → **回滚只回滚了指针，版式没回滚** |
| `jimu_report` | 真正的版式（`json_str` = Excel 设计 JSON）+ 打印钩子（`js_str`）+ 视图ID | 与 `t_print_template` 是**两个事实来源**；版本不受控 |
| `jimu_report_db` / `_field` / `_param` | 数据集 / 字段 / 参数（数据接线） | 靠 `sql/s6_2、s18、s22、s25` 和 `tests/import-hotel-print-samples.mjs` **直接写库**维护，每套模板克隆一份 |
| `t_delivery_print_log` | 打印分界（客户+日期+点） | 在用，保留 |
| `t_print_preview_log` | 预览留痕 | 仅历史送货单链路调用，无门禁实际拦截，近似死代码 |
| `t_print_asset` | W0-6 打印资源 | `s23` 已列退役（前端 0 调用） |

### 1.2 运行时链路（现状，已跑通）

```
选主体(bizKey) → GET /print/resolve-template → selectBindTemplate(t_print_template, status=2)
              → POST /print/ticket (bizKey 绑定) → window.open(/jmreport/view/{content}?ticket=…)

```

链路本身是好的（PT-1~4 已落地）。问题集中在**模板/报表的「维护面」**，不在「打印面」。

## 二、目标架构（to-be）

### 2.1 分层与职责（单一事实来源）

```
┌──────────────────────────────────────────────────────────────────┐
│ L4 打印面（不变）  /print/resolve-template → /print/ticket → view   │
│                    → 数据集回调 → /print/receipt → 打印分界          │
├──────────────────────────────────────────────────────────────────┤
│ L3 渲染产物（物化，可重建）  jimu_report + jimu_report_db(_field/_param) │
│     · 由物化器从「模板 + 数据契约」生成，不再手工维护                  │
│     · 发布产物不可变（published_report_id）；草稿产物可改（draft_report_id）│
├──────────────────────────────────────────────────────────────────┤
│ L2 模板注册（唯一事实来源）  t_print_template                       │
│     · 绑定/形态/联数/状态/版本 + draft_report_id + published_report_id │
│     · 版本快照 t_print_template_version 含 design_json + dataset_spec │
├──────────────────────────────────────────────────────────────────┤
│ L1 数据契约（唯一数据口径）  PrintDataContract                      │
│     · MATRIX: head/columns/rows(wide|long)；FLAT: head/rows         │
│     · 字段字典 + 参数 + 端点，供「生成器/物化器/预览/设计器字段面板」共用│
└──────────────────────────────────────────────────────────────────┘
```

### 2.2 核心决策

| 决策 | 内容 | 解决的问题 |
|---|---|---|
| **PR-D1 单一事实来源** | `t_print_template` 管业务与版本；`jimu_report` 是**物化产物**，不手工建 | PR-A1/A4/B4 |
| **PR-D2 发布即克隆** | 发布时把草稿报表 `json_str` 克隆为**新的不可变报表** `published_report_id`，并把 `design_json` 快照进版本表 | PR-A1/A2 |
| **PR-D3 契约驱动物化** | 数据集/字段/参数由 `PrintDataContract` 生成，URL 来自配置项 | PR-A4/B4 |
| **PR-D4 动态生成骨架** | `PrintTemplateGenerator` 按形态+客户实际结构（点数×班次）生成设计 JSON，替代静态 JSON 导入 | PR-A3/C2 |
| **PR-D5 真实数据预览** | `preview-data`（数据面板）+ `preview-view`（iframe 内预览），预览票据**不登记打印分界** | PR-C1 |
| **PR-D6 清理** | 删除静态样板导入、死字段、旧前端 print 模块、无用表 | PR-A3/B2/B5 |

### 2.3 模板生命周期（目标）

```
新建 → [生成骨架 or 从全局模板复制] → 草稿(draft_report_id 可设计)
     → 预览(真实数据/真实版式) → 测试发布(status=1, 水印)
     → 正式发布(status=2)：克隆报表为 published_report_id + 版本快照(design_json+dataset_spec)
     → 打印走 published_report_id
     → 再编辑：从 published 分叉新 draft → 发布生成新版本
     → 回滚：以历史版本 design_json 重建报表 → 发布为新版本（历史不覆盖）
```

### 3.3 数据契约（新增，代码内 + 可查询）

```java
public final class PrintDataContract {
    // 形态
    enum Form { MATRIX, FLAT }
    // 字段：code, text, type, section(head/columns/rows), required
    record Field(String code, String text, String type, Section section, boolean required) {}
    // 参数：code, text, defaultValue, section
    record Param(String code, String text, String defaultValue) {}
    // 数据集：dbCode, dbChName, isList, apiConvert, endpoint
    record DataSet(String dbCode, String chName, boolean list, String convert, String endpoint) {}

    static List<Field> fields(Form form, RowsShape shape); // wide|long
    static List<DataSet> dataSets(Form form, RowsShape shape);
    static List<Param> params(Form form);
}
```

- 新增 `GET /print/contract?form=MATRIX&rowsType=long` 返回字段字典/参数/数据集描述。
- 前端「字段面板」、生成器、物化器、预览校验**共用同一份契约**，杜绝字段漂移。

## 四、动态生成（替代静态 JSON 导入）

### 4.1 模板骨架（Blueprint，随代码版本管理）

- 资源文件：`lin-distribution/src/main/resources/print-blueprint/{form}-{style}.json`
  - `matrix-long.json`（横向动态列，**通用**，客户无关）
  - `matrix-wide.json`（槽位套打，槽位数参数化 `{{slots}}` / `{{colNames}}`）
  - `flat-a4.json`（点单 A4）
  - `flat-dot.json`（点单针式，可选）
- 骨架只放**版式**（行列/样式/合并/分页），字段绑定用契约 code 占位（如 `{{hm.customerName}}`、`{{dd.productName}}`）。

### 4.2 生成器

```
POST /print/template/generate
{
  "printForm": "MATRIX",
  "rowsType": "long",              // long=动态列 / wide=槽位套打
  "customerId": 11,                // 用于推导标题、点数×班次
  "deliveryDate": "2026-09-01",    // 可选：按当日实际布局推导槽位（wide 用）
  "paper": "A4", "layout": "landscape",
  "title": "大长江总单",            // 缺省 = 客户名+总单
  "note": "点心早上6点送到"         // 可选页脚/提示
}
→ { designJson, slots, columns:[{deptId,deptName,shiftCode,label}], contract }
```

生成规则：

| 形态 | 槽位/列 | 是否需客户级模板 |
|---|---|---|
| MATRIX + long | 横向动态列（`groupRight(deptLabel)`），槽位=∞ | **不需要**：一份全局模板服务所有客户（标题动态 `${hm.printTitle}`） |
| MATRIX + wide | 槽位 = Σ(启用点 × 班次) + 历史停用点 adHoc 数（与 `docs/assets/print/hotels/README.md` 口径一致） | 需要（套打列位固定） |
| FLAT | 一维明细 | **不需要**：一份全局模板；仅当纸张/联次/签收栏不同才建客户级 |

> 结论：**默认不生成客户级模板**。只有「套打列位固定」或「客户纸面有专属版式」时才生成客户级，
> 且生成结果可继续在设计器微调。这样既满足「动态生成」，又不制造一堆冗余模板（PR-B6）。

### 4.3 与当前数据/表结构结合

生成器读取的真实结构来源：

| 需要的信息 | 来源表 |
|---|---|
| 客户名/别名（标题） | `t_customer.name / alias` |
| 配送点（列） | `t_customer_dept`（parent_id>0、启用、sort） |
| 班次（列后缀） | `t_customer.shift_enabled` + `t_customer_dept.shift_codes` + 字典 `biz_shift_type`（复用 `util/ShiftCodes`） |
| 当日实际布局/历史 adHoc | `DeliveryBatchService#selectMatrix` 的 `columns`（与打印取数**同源**，避免两套口径） |

> 关键：**生成器的列推导必须调用 `selectMatrix` 的布局结果，而不是自己再写一套**，保证「模板列 = 纸面列 = 数据列」。

## 五、积木报表维护（物化）

### 5.1 物化器 `JimuReportMaterializer`

```
ensureReport(templateId, mode=DRAFT|PUBLISHED) → reportId
  1) 取模板 design_json（草稿取 draft；发布取发布入参）
  2) upsert jimu_report(id, json_str=design_json, js_str=打印钩子(v=配置), name, code)
  3) ensureDataSets(reportId, form, rowsType)   ← 契约驱动，自动建/更新
  4) ensureFields(reportId, contract.fields)    ← 自动建/更新 jimu_report_db_field
  5) ensureParams(reportId, contract.params)    ← 自动建/更新 jimu_report_db_param
  6) 返回 reportId
```

- 全部幂等（按 `jimu_report_id + db_code`、`field_name`、`param_name` upsert）。
- `api_url` 由配置项拼接：`lin.print.api-base-url`（默认取 `server.servlet.context-path` 或显式配置），
  **消灭 `http://localhost:8090` 硬编码**（PR-A4）。
- 打印钩子版本（`print-annotation.js?v=N`）由配置项 `lin.print.annotation-version` 统一，消灭散落 SQL（s26）。

### 5.2 共享数据集（推荐，需验证）

JimuReport 2.0.0 的 `jimu_report_db` 已有 `iz_shared_source` / `jimu_shared_source_id`：

- 建立 2 套共享数据集：`MATRIX`（hm/hc/dc/dm）、`FLAT`（hd/dd），`iz_shared_source=1`；
- 各模板报表通过 `jimu_shared_source_id` 引用，**不再逐报表克隆**；
- 若共享机制在 2.0.0 上行为不符，回退方案：物化器从「契约模板报表」克隆数据集（仍全自动，只是每报表一份）。

> 这一条直接消灭 `tests/import-hotel-print-samples.mjs` 里「从参考模板克隆数据集」的整套逻辑（PR-A4）。

### 5.3 发布 / 回滚 / 删除（目标语义）

| 动作 | 目标实现 |
|---|---|
| 测试发布 | 物化 DRAFT 报表 + `printConfig.watermark` 写测试水印；status=1；**不生成版本** |
| 正式发布 | 校验门禁（字段绑定都能在契约中解析）→ 物化 PUBLISHED 报表（新ID，不可变）→ 版本快照(design_json+dataset_spec+report_id) → status=2 |
| 回滚 | 取版本 `design_json` → 物化 PUBLISHED 报表 → 写新版本（不覆盖历史） |
| 删除 | 已发布仅停用（status 增加 DISABLED 或 `is_deleted=1`）；未发布物理删并清理 draft/published 报表 |
| 导出 | 导出 `design_json` + `dataset_spec` + 元数据（**真实可用**，修 PR-A2） |
| 导入 | 导入为草稿（design_json + 契约版本），**物化时自动重建数据集**，重走发布门禁 |

## 六、真实数据预览（本次核心体验）

### 6.1 预览主体

预览主体与打印主体同构（`PrintBizKeys`）：`matrix:{customer}:{date}` / `point:{customer}:{dept}:{date}`。

### 6.2 预览接口

## 十、验收标准

1. **版本可回滚版式**：发布 v2 改版式 → 回滚 v1 → 打印/预览纸面回到 v1 版式（不再只回滚指针）。
2. **导入导出可用**：任意真实模板可导出为开放包并重新导入为草稿，导入后预览有真实数据。
3. **加模板零 SQL**：新建一个客户级模板全程在应用内完成（生成/设计/预览/发布），不写任何 SQL、不碰 `jimu_report_*`。
4. **真实数据预览**：打印模板页可选定「客户+日期+点」，同屏看到真实订单数据（字段→值）与真实版式预览，且**不翻转打印分界**。
5. **动态生成**：给定客户，一键生成与「当日实际布局」列一致的模板（列 = `selectMatrix` 列），无需导入静态 JSON。
6. **无 localhost 硬编码**：数据集 URL 由配置生成，换环境无需改库。
7. **死代码归零**：静态样板导入、旧前端 print 模块、`t_print_asset`、无用字段/表全部移除，测试全绿。

### P5 评估结论（缓行，需业务确认）

| 项 | 结论 | 理由 |
|---|---|---|
| `t_print_template` 死字段收敛（`data`/`render_engine`/`type`） | **缓行** | `data` 为 `NOT NULL` 且 mapper 硬编码 `'{}'`，DROP 列需同步改 mapper，属破坏性 DDL；收益仅“少两个恒值列”。已备可选脚本 `sql/s40_print_field_convergence.sql`（默认注释） |
| `is_default` 合并入 `bind_type=3` | **不做** | `selectBindTemplate` 实际依赖 `bind_type=3 AND is_default='1'`，并非冗余 |
| 4 个客户级宽表模板合并为全局 | **需业务确认** | 它们是**宽表套打**且槽位数按客户布局定格；是否改用全局长表是版式业务决策，不由代码单方定 |
| 共享数据集（`iz_shared_source`） | **不做** | P2 的 `ensureMaterialized` 已使数据集维护全自动，逐报表一份不再构成维护负担；共享数据集收益降低且需 JimuReport 渲染验证 |
| `PrintPreviewLog`/`recordPreview` | **缓行** | 无门禁意义；现已有真实预览（P4），若要保留可改造为预览埋点，非清理必需 |
